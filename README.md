# 简历岗位雷达 v2 · 个人求职工作台

新版提供工作台、岗位库、投递进度、简历与目标、来源设置五页。Web / CLI / Electron 共用版本化工作区；确认画像后可按新版本重评分，人工投递记录独立保留。旧参数和 v1 API 继续可用。详见 [v2 升级指南](docs/v2-upgrade-guide.md)。

桌面开发安装：`npm ci --ignore-scripts` → `node tools/fetch-electron.mjs` → `npm run dist:desktop`。下载器验证官方 SHA-256；正式包保留 sandbox/contextIsolation，桌面密钥使用系统加密。

# 使用与兼容参数

**根据大学生简历关键词，自动去全网匹配对口岗位。**

粘贴或上传一份简历 → DeepSeek 提取求职画像与岗位关键词 → 检索真实岗位 → 按匹配度打分排序 → 给出「为什么匹配」和「差在哪」→ 导出 CSV / Markdown。

面向**中国大陆校招 / 实习**市场。

支持三种运行方式：

| 模式 | 适用场景 | 入口 |

## 桌面应用（exe）

**双击就能用，不需要装 Node.js、不需要开浏览器、不需要敲命令。**

### 直接使用

打开 `dist\简历岗位雷达-win32-x64\`，双击 **`简历岗位雷达.exe`** 即可。

整个文件夹就是免安装版，可以整体拷到 U 盘或别的 Windows 电脑上直接运行（无需安装，也无需管理员权限）。

首次启动后：

1. 界面会自动展开「使用我自己的 DeepSeek API Key」，填入你的 Key（[申请地址](https://platform.deepseek.com/)）
2. Key 会保存在你本机，下次打开无需重填
3. 粘贴简历 → 点「开始全网检索」

> 不想填 Key 也能跑，但会退化成离线规则模式，岗位匹配质量明显下降。

### 菜单功能

| 菜单 | 能做什么 |
| --- | --- |
| 文件 | 打开数据目录 / 打开配置文件 / 打开历史结果目录 |
| 编辑 | 撤销、复制、粘贴（粘贴简历全靠它） |
| 视图 | 刷新、缩放、全屏、开发者工具 |
| 帮助 | 获取 DeepSeek Key、获取搜索 Key、关于（含数据目录与本机服务地址） |

### 数据存在哪

桌面版为了能装进只读的应用包，把数据写到了用户目录：

```
C:\Users\<你>\AppData\Roaming\ResumeJobRadar\
├── config.json          配置（首次启动自动生成，可手改）
├── font-map.json        实习僧字体映射缓存
├── quota.json           当日配额计数
└── runs\                每次检索的完整结果
```

从菜单「文件 → 打开数据目录」可直接打开。

### 自己打包

```bash
npm install                        # 安装依赖
node tools/fetch-electron.mjs      # 下载 Electron 运行时（约 130MB，走国内镜像）
node tools/make-icon.mjs           # 生成应用图标
npm run dist:desktop               # 打包
```

产物：

```
dist\简历岗位雷达-win32-x64\
├── 简历岗位雷达.exe      ← 200MB，主程序
├── resources\app.asar    ← 36MB，应用代码 + 生产依赖
├── locales\              ← 语言包（已精简到 4 个，省 42MB）
└── *.dll / *.pak / *.bin ← Electron 运行时
```

整包约 **318MB**（Electron 应用体积主要来自 Chromium 内核，属正常范围）。打包耗时约 5 秒。

### 验证桌面版

```bash
npm run test:desktop        # 启动内置服务并断言 15 项关键行为，不弹窗
```

若要看真实窗口是否正常，直接双击 exe 即可；也可以在命令行运行
`简历岗位雷达.exe --self-test` 让它自检后立即退出。

### 打包实现说明

打包流程是**自研的**（`tools/build-desktop.mjs`），没有用 `@electron/packager`：

- packager 内部用 `extract-zip` 解压 Electron，而该库在本项目环境下会「建完第一个目录就永久卡住」
  （当时用隔离复现脚本确认过与权限无关；该复现脚本已在后续清理中移除）；
- 因此改用自研解压器（`tools/lib/unzip.mjs`，同一个 130MB 包 1.4 秒解完），
  再用纯 JS 的 `@electron/asar` 打 asar、用 `resedit` 写图标与版本信息，全程无子进程依赖。

另外刻意排除了 `@napi-rs/canvas-win32-x64-msvc`（36MB 原生渲染库）——它只用于把 PDF
渲染成图片，而本工具只做文本提取。启动时可能看到一句 `Cannot load "@napi-rs/canvas"` 警告，
属预期行为，不影响功能。

## 快速开始（本地网页版）

### 1. 环境要求

- **Node.js 20 或更高版本**（[下载](https://nodejs.org/)）
- 一个 **DeepSeek API Key**（[申请地址](https://platform.deepseek.com/)）——可选，但没有它匹配质量会明显下降

### 2. 启动

**Windows 用户最简单的方式**：双击 `start.cmd`，它会自动装依赖、生成配置、打开浏览器。

**手动方式**：

```bash
cd 简历脚本
npm install          # 首次运行，安装 PDF 解析依赖
npm start            # 启动服务
```

然后浏览器打开 **http://127.0.0.1:3210**

### 3. 配置 DeepSeek Key

按以下任一方式提供密钥（优先级从高到低）：

1. `config.json` 里的 `deepseek.apiKey`
2. 环境变量 `DEEPSEEK_API_KEY`
3. 若你已安装 DSH，会自动读取 `~/.dsh/.credentials.yaml` 中的凭据

```bash
copy config.example.json config.json    # Windows
cp config.example.json config.json      # macOS / Linux
```

编辑 `config.json`：

```json
{
  "deepseek": {
    "apiKey": "sk-你的密钥"
  }
}
```

### 4. 先跑个自检（推荐）

```bash
npm run doctor
```

它会逐项确认 Node 版本、DeepSeek 连通性、搜索通道、智联/实习僧数据通道、PDF 解析依赖是否正常。

## 在线部署（公网 / 多人使用）

想让别人通过网址访问，请先看 **[`deploy/部署指南.md`](deploy/部署指南.md)**（含云服务器、Docker、PaaS、HTTPS 全套步骤）。

最快的路径：

```bash
cp .env.example .env      # 填入 AUTH_PASSWORD 和 DEEPSEEK_API_KEY
docker compose up -d --build
```

然后在宿主机用 `deploy/nginx.conf` 或 `deploy/Caddyfile` 反代并配置 HTTPS。

### 为什么要这么麻烦

这个应用会带着**你的 DeepSeek Key**和**你的服务器 IP**去访问招聘网站。
一旦公开暴露又没有防护，任何人都能消耗你的额度、并用你的 IP 去抓取别人网站。
所以做了这些防护：

| 防护 | 说明 |
| --- | --- |
| **fail-closed 启动校验** | 监听公网地址但没配登录口令时，**服务直接拒绝启动**并给出修复指引 |
| **密码登录** | scrypt 哈希 + HMAC-SHA256 签名会话；HttpOnly / SameSite=Lax Cookie |
| **暴力破解防护** | 同 IP 连续失败 5 次锁定 15 分钟（可配） |
| **CSRF 防护** | SameSite=Lax + 校验 Origin/Referer |
| **并发闸门** | 默认最多 2 个任务同时跑，其余排队，队列满则拒绝 |
| **每日配额** | 全站 100 次/天 + 单 IP 10 次/天，**持久化到磁盘，重启不重置** |
| **代理感知限流** | 只有显式 `TRUST_PROXY=1` 才信任 `X-Forwarded-For`，否则该头可被伪造绕过限流 |
| **安全响应头** | CSP、X-Frame-Options、nosniff、Referrer-Policy，HTTPS 下追加 HSTS |
| **密钥隔离** | DeepSeek Key 只在服务端；未登录时 `/api/health` 不返回任何密钥信息 |

### 让访客自带 Key（推荐）

公开站点最怕额度被刷爆。默认已开启「用户自带 Key」：
访客在检索页展开 **「使用我自己的 DeepSeek API Key」** 填入自己的密钥即可，
费用由使用者承担，你只提供算力与抓取通道。

该 Key 只随单次请求发送、存在浏览器 `sessionStorage`，**服务端不落盘、不写日志**。

### 安全测试

```bash
npm run test:security
```

66 项测试覆盖密码哈希、会话签名与篡改、登录限速、并发与配额闸门、
代理 IP 解析、fail-closed 校验、以及完整的 HTTP 鉴权流程。

## 只要某一届的校招（届别过滤）

比如「只要 2027 届毕业生校招」，在界面上选 **目标届别 = 2027 届**，并取消勾选「含实习岗」即可。

也可以在 `config.json` 里固化：

```json
"filters": {
  "graduationYear": "2027",     // 目标届别；留空 = 不过滤
  "includeInternship": false,   // 是否保留实习岗
  "strict": true,               // true = 硬过滤；false = 只标记不剔除
  "yearQueryCount": 3,          // 用几个「届别」检索词去招聘站搜校招岗
  "cities": []                  // 期望城市：null=从简历推断，[]=不限城市，["北京"]=指定
}
```

界面上「期望城市」留空即按配置走，填 **「全国」** 表示不限城市。

### 它到底怎么判断届别

各数据源的信号强弱差别很大，所以做的是**分层判定**，而不是简单关键词匹配：

| 信号 | 来源 | 强度 |
| --- | --- | --- |
| `jobType` 明确写着「社招」 | 数据源/LLM | 最强，直接判社招 |
| `graduationYear` 结构化字段 | 牛客校招 | 最强，直接就是「2027届」「毕业不限」 |
| `workType === '校园'` | 智联招聘 | 站点官方校招标记 |
| `batch`（如「2027届秋季校园招聘」） | 公众号（LLM 抽取） | 强 |
| 「校园招聘 / 校招 / 秋招 / 春招 / 管培生」 | 全部来源 | 强 |
| 「2027届」「27届校招」 | 全部来源 | 中 |
| 「应届 / 毕业生」**单独出现** | 全部来源 | 弱，不足以判定 |
| 经验要求「3年以上」 | 全部来源 | 用于判定**不是**校招 |

判定结果分四类：`校招` / `实习` / `社招` / `届别不明`，然后：

- 数据源自己标了**社招**，或要求 1 年以上经验且无强校招信号 → 剔除
- 明确写了**其他届别**（如 2026届、2028届）→ 剔除
- **实习岗** → 按「含实习岗」开关决定
- **校招但没写具体届别** → 保留（很多校招公告确实不写届别）
- **什么线索都没有** → `strict: true` 时剔除

#### 两个踩过的坑

**① 只判断「有没有出现应届」太宽松。**
`java后端开发工程师（接受应届毕业生）`、`【高薪兜底｜应届可冲】` 这类**社招但接受应届**的岗位会被误放行。
现在要求出现「校园招聘 / 校招 / 秋招 / 春招 / 管培生」这类**校招项目措辞**才算校招。

**② 公众号文章的推广页脚会污染届别判断。**
一篇「诚招 Java 后端 1 人（要求 2 年经验）」的社招文章，页脚写着
「加入 2027届央国企求职信息群」——年份检测捞到 2027，于是一个纯社招岗位被当成了 2027 届校招。
现在**数据源标注的 `jobType` 优先于从正文里捞年份**，并且「要求 1 年以上经验 + 无强校招信号」会直接判为社招。

另外还有一处容易忽略的地方：**画像里的毕业年份会被校正为目标届别**。
否则会出现「按 2027 届筛岗位、却拿 2026 届的画像去精排」的矛盾，LLM 会把对口岗位判成届别不符。

### 实测效果

以示例简历（Java 后端，**不限城市**）跑真实数据：

```
采集 1358 条 → 去重 991 条
届别过滤：991 → 166 条（剔除 334 条社招 + 480 条实习 + 10 条其他届别 + 1 条届别不明）
精排后 26 条，全部是 2027 届校招，零社招泄漏
比较匹配 6 条 / 一般匹配 10 条 / 弱匹配 10 条

  1. [牛客校招]       【秋招正式批】拼多多后端工程师       @拼多多集团-PDD
  2. [智联招聘]       java全栈开发（27届）                 @久远银海
  3. [高校就业网·西电] Java开发工程师（上海）-用增-2027届   @广州希音国际进出口
  4. [高校就业网·郑大] 后端开发-校招（J15306）             @北京掌上先机网络科技
  5. [高校就业网·大连海事]【特福国际】IT校招储备（JAVA开发）@广州市森大贸易
  6. [牛客校招]       Agent研发工程师                     @字节跳动
  7. [智联招聘]       软件开发工程师（面向2027届毕业生）     @西安华为技术有限公司
   + 6 条牛客校招日程（小红书 / 拼多多 / 携程 / 正浩创新 / 金智科技 / 乐享元游 网申中）
```

### 关于 `shortlistSize`

规则预筛后进入 LLM 精排的岗位数，默认 150。
届别过滤后岗位池通常只剩一两百条，这个值要足够大，否则对口的校招岗位会被规则分挡在评分之外
（实测 60 → 150 时，结果从 9 条增加到 23 条）。调大的代价是 LLM 调用次数与耗时。

> **高校就业网这条源单独贡献了 3 个高质量对口岗位**（希音、掌上先机、森大贸易），
> 而这些岗位在智联和实习僧上都没有出现 —— 这正是加它的意义。
>
> 同一份简历跑「关闭 LLM」的离线模式会得到 43 条，但以「弱匹配」为主 ——
> 规则预筛无法判断一条「XX机械总院2027届校园招聘」公告里到底有没有 Java 岗。
> **LLM 精排在这里作用很关键**：它把 12 条高校公告里真正对口的 3 条挑了出来。

### 一个提醒：别把「校招」和「实习」混在一起看

实习僧的岗位量远大于校招岗。如果打开「含实习岗」，实习会占满结果列表，
真正的校招岗会被挤到后面——所以**默认是不含实习**的。
想看实习时再单独打开开关，或直接不带届别跑一次。

## 把目标钉死（画像覆盖）

如果你要把这个工具**固定服务于一个特定目标**（比如「就盯中国民用航空飞行学院、消防工程」），
不希望每次 LLM 解析简历的波动影响选校与检索词，可以在 `config.json` 里钉死画像：

```json
{
  "profile": {
    "school": "中国民用航空飞行学院",
    "major": "消防工程"
  }
}
```

| 钉死项 | 影响 |
| --- | --- |
| `school` | 高校就业网的**本校自动探测**目标 |
| `major` | **按专业选校**、**检索词生成**、**岗位方向判定**、打分里的专业适配 |
| `targetRoles` | 目标岗位词（会以最高权重 100 参与岗位族推导） |
| `skills` / `graduationYear` / `preferredCities` | 同名字段，一般不需要钉 |

行为细节：

- 只钉 `school` / `major` 时，`targetRoles` 会**按新专业自动推导**，并清掉简历里残留的旧方向 ——
  否则旧 `targetRoles` 的权重是 100，会把新专业推导出来的岗位族（权重 40）整个压住，
  出现「专业钉死成消防工程、检索词却还是 Java后端」的自相矛盾。运行日志会明确打印这几次替换。
- 以 `_` 开头的键（如 `_说明`）是注释，不会被当成画像字段。
- 留空 `profile: {}` = 完全按简历来。

实测（把一份 Java 简历钉死成民航飞行学院 / 消防工程）：

```
画像已按配置钉死：school: "北京邮电大学" → "中国民用航空飞行学院"；
                major: "计算机科学与技术" → "消防工程"；
                targetRoles: ["后端开发工程师"] → ["消防工程师","消防安全","消防设计","安全工程",…]（按钉死专业推导）

站点检索词：消防工程师、消防安全、消防设计、安全工程、安全工程师、EHS工程师、安全管理、安全评价、2027届…
```

## 消防 / 安全工程专业支持

这套工具原本的词表是 IT / 商科向的，对**消防工程、安全工程、应急管理**这类专业几乎为零覆盖，
会出现「技能分（权重 45）拿不到分、岗位方向判成别的行业」的问题。现在已经补上：

- **技能词表**新增 60+ 个消防/安全/民航词：建筑防火、火灾自动报警、自动喷水灭火、防排烟、
  防火分区、消防验收、安全评价、风险辨识、隐患排查、应急预案、危险化学品、EHS、
  民用航空、机场运行、BIM/Revit/广联达/PKPM…
- **岗位族**新增 `fire-safety` 族，并**排在 IT 安全族之前**，避免「消防安全」被 IT 安全吃掉。
- **离线画像**新增消防/安全岗位识别规则。

### 「安全工程师」同名陷阱

这是这个方向最容易踩的坑：**「安全工程师」既是消防/安全工程的岗位，也是 IT 网络安全的岗位。**

消防工程的学生搜「安全工程师」，在理工类院校就业网上捞回来的几乎全是「网络安全工程师」——
实测西电一所学校就返回 10 条这类岗位。更麻烦的是归一化后 `'网络安全工程师'.includes('安全工程')` 为真，
于是这些岗位会命中岗位族里的「安全工程师」，白拿 22 分方向分。

现在做了三层处理：

| 处理 | 效果 |
| --- | --- |
| **检索词排序**：`消防*` 排在最前 | 高校就业网只取前 3 个词 → `消防工程师 / 消防安全 / 消防设计`，全部无歧义 |
| **跨方向判定** `isCrossDomainSecurity` | 画像是消防/安全工程、标题含 `网络安全/信息安全/渗透/等保` 且剥离 IT 安全词后不含消防特征 → 撤掉方向分 |
| **歧义技能词不计分** | 跨方向岗位的「安全工程/安全管理/安全生产」等命中不计入技能分（这些词在网安语境里是另一个意思） |

效果（同一份消防画像）：

```
消防工程师（2027届校招）        65 → 91 分   方向命中：消防工程师 / 安全工程师
安全管理员（生产现场安全隐患）    55 分       方向命中：安全管理
网络安全工程师（27届校招）        48 → 26 分   方向分被撤，低于 minScore=40 被过滤
```

> 反方向也做了防护：ROLE_FAMILIES 里的「安全工程」用了负向后顾 `(?<!网络)(?<!信息)`，
> 一个做渗透测试的人不会同时被推成消防工程师。

## 用「毕业生去向」做补充数据源

只按岗位标题关键词搜，会漏掉一大批**标题里不写专业名**的对口岗位。
例如消防工程专业，「危险品培训专员」「隐患治理专员」「场道维护员」「机场消防」这些
确实是对口岗，但标题里一个「消防」都没有。

这些岗位从哪找？**看学校官方发布的毕业生去向** —— 就业质量报告和专业简介里会明确写出
毕业生实际去了哪些单位、哪些行业，这是最权威的依据。

数据存在 `src/match/destinations.mjs`，**只收录原文明确写到的内容，不做推测**，每条都带出处 URL。

### 已收录

**中国民用航空飞行学院 · 消防工程**
（来源：[消防工程专业简介](https://www.cafuc.edu.cn/jwcx/info/1185/1535.htm)，2026-09 采集）

| 项 | 内容（均为原文明确写到） |
| --- | --- |
| **就业单位** | 上海浦东国际机场、上海虹桥国际机场、深圳宝安国际机场、中安保实业集团有限公司、四川川消消防车辆有限公司、广州白云国际机场、乌鲁木齐天山国际机场 |

这些数据会转成 8 个补充检索词注入检索计划：

```
机场消防、航空安全、应急救援、危险品、消防安全管理、机场运行、安检、消防设施操作员、新能源安全、铁路安全
```

除了当检索词，`matchesDestination()` 还用于判断岗位是否命中去向单位/行业（行业匹配用模式而非字面，
否则「航空公司」匹配不到「圆通航空集团」「海航航空技术」这些真实的航司名）。

### 加自己学校/专业

在 `DESTINATIONS` 里追加一条即可，关键是 `extraQueries` —— 把**标题里不会出现专业名、但确实对口**的岗位叫法写进去：

```js
{
  school: 'XX大学', major: '消防工程',
  employers: [...], industries: [...], roles: [...],
```

## 高校就业网：晨云智慧就业系统

除了才立方，还有学校用**「晨云智慧就业管理服务系统」**（技术支持：成都晨云信息技术有限责任公司）。
**中国民用航空飞行学院用的就是这套**，已收录并实测可抓。

这套系统的坑：

| 坑 | 说明 |
| --- | --- |
| **未知路径一律返回首页** | 访问任何不存在的路径都返回首页 HTML（72KB），所以按才立方的路径特征去探测会一律判为「不支持」—— 这就是最初把 `jy.cafuc.edu.cn` 判错的原因 |
| **列表必须 POST** | `POST /index/index/employjoblistdata.html`，body `page=N`。用 GET 会抛 `think\exception`（`Undefined array key "page"`） |
| **不支持关键词过滤** | `keyword` / `search_key` / `key` 全被忽略，`title` 参数直接报错。策略改为：全量翻页 → 本地按关键词排序 → 只抓高相关的详情 |
| **出错返回 PHP 调试转储** | 必须显式识别 `think\exception` / `<pre>array(`，否则会被当成「没数据」静默吞掉 |

岗位量很小（实测中飞院 2 页约 25 条），全量翻页成本可接受。列表页提供
标题 / 公司 / 城市 / 类型 / 学历，详情页提供岗位要求正文 / 专业 / 招聘人数 / 截止日期。

实测（2026-09）：


## 就业桥：覆盖院校面最广的源

`{学校缩写}.jiuyeqiao.cn` 是一套**按学校开子域**的商用平台。实测 **20/20 所**测试院校全部覆盖
（每校 196–253KB 服务端渲染页面），其中包括**北邮、电子科大、杭电**等自建就业网抓不到的学校
（那些学校我花 400 次探测都没找到可用入口，但就业桥上有）。

更关键的是它有**跨校岗位库 + 服务端关键词过滤**：

```
https://job.jiuyeqiao.cn/zhiwei/0/?keywords=消防&page=2
```

所以**拉岗位不需要枚举学校** —— 一次开发就覆盖了大量院校的生源岗位。这是目前性价比最高的一个源。

| 接口 | 说明 |
| --- | --- |
| 列表 | `GET /zhiwei/0/?keywords=<词>&page=<N>` → `<ul class="ul-main-list">` 内 10 条/页 |
| 字段 | `.list-job` 岗位 / `.list-company` 公司 / `.salary` 薪资 / `.list-condition` 城市·类型·经验·学历·人数 |
| 详情 | `GET /zhiwei/<id>.html` |

两个解析坑（都已修）：

- **`class` 带额外类名**：实际是 `class="list-company fr"`，写死 `class="list-company"` 会全部匹配不到
- **城市在 `.list-condition` 里**，不在 `.list-addr`（后者是侧栏「热招职位」用的），
  按 `.list-addr` 取会抓到「人事部门」这种噪声

实测效果（消防工程画像，2026-09）：

```
就业桥：检索 3 次，列表 25 条，抓详情 8 条，得到 8 个岗位

  · 消防设施维保员  @京沃消防维保技术（辽宁）  沈阳  4K-8K/月  大专
  · 消防中控员     @京沃消防维保技术（辽宁）  沈阳  5K-9K/月  大专
  · 应急救援员     @京沃消防维保技术（辽宁）  沈阳  5K-1W/月  大专
  · 消防维保       @河北烽盾安全技术       南阳/商丘/信阳/周口/驻马店  3K-5K/月
```

接入流水线后，**最终 20 条结果里有 4 条来自就业桥，第 1 名就是「消防工程师」**。

## 证书与技能熟练度进打分

原来这两项完全没用上 —— 消防简历里的「注册消防工程师」「安全员C证」被当成普通关键词，
「Java（熟练）」和「Python（了解）」命中同一个岗位也同分。

**新增两个加分维度**（加法式，不削减原有权重，总分仍封顶 100）：

| 维度 | 分值 | 说明 |
| --- | --- | --- |
| `cert` 证书匹配 | 0–6 | 岗位提到你已有的证书 → +6；岗位要求你没有的证书 → 0 分但**写进 gaps 提示**（「优先/加分」不算硬要求） |
| `prof` 熟练度 | 0–4 | 按简历里的等级加权：精通/熟练 1.0、掌握/熟悉 0.8、了解 0.4、未标注 0.6 |

覆盖 15 类常见证书：注册消防工程师、消防设施操作员、注册安全工程师、安全员证、初级/中级会计、
CPA、ACCA、法律职业资格、教师资格证、英语四六级、计算机二级、软考、驾照。

实测：

```
消防工程师（2027届校园招聘）  有证书 79 分 {role:22, skill:19, city:15, meta:13, cert:6, prof:4}
                            无证书 73 分 {role:22, skill:19, city:15, meta:13, cert:0, prof:4}

reasons: 岗位提到「注册消防工程师」，你已有
gaps:    岗位要求「中级会计」，简历中未见
```

## 岗位数据从哪来

系统内置三条通道，**互不依赖**：

### 通道一：站点直连（零 API Key，开箱即用）

| 数据源 | 覆盖 | 单次抓取量 | 说明 |
| --- | --- | --- | --- |
| **智联招聘** | 社招 + 部分校招 | 每关键词最多 5 页 × 20 条 | 列表页内嵌结构化数据，含职位名、公司、薪资、城市、学历、经验、技能标签；详情页可拿完整 JD 正文 |
| **实习僧** | 实习 / 校招实习 | 每关键词最多 3 页 × 20 条 | 含公司、城市、学历、日薪、技能与福利标签；岗位标题有字体混淆，见下方说明 |
| **牛客校招** | 校招（含届别） | 20 个岗位 + 20 条校招日程 | **岗位自带 `graduationYear` 字段**（「2027届」「毕业不限」），是届别筛选最可靠的来源；另有校招日程（公司维度网申窗口） |
| **高校就业网** | 各企业官方校招公告 | 每校每词 15 条，单次最多抓 12 条详情 | **企业把官方校招信息发布到高校就业网**。页面服务端渲染、可直接解析，含薪资/城市/学历/需求专业，公告里还常带职位表。**按简历的学校与专业自动选校**，无需手工配置 |
| **微信公众号** | 校招 / 秋招 / 实习公告 | 每关键词 10 篇，单次最多抓 10 篇正文 | 企业校招公告的主战场。经搜狗微信公开通道检索，**无需登录微信**；正文由 DeepSeek 抽取成结构化岗位 |

> 这些站点的列表页在服务端渲染时内嵌了结构化数据，本工具通过解析这些内嵌数据获取岗位，**不执行页面 JS、不模拟登录、不绕过验证码**。

#### 关于高校就业网

**为什么不去抓企业自己的招聘官网**：实测过字节、华为、美团、京东、小米、腾讯、网易、百度、大疆等的校招官网，
**全部是纯前端渲染 + 需鉴权的接口**（字节首页 811KB 但只是空壳；京东接口返回 `{"code":401}`），拿不到岗位数据。

但企业会把**同一份官方校招信息发布到高校就业网**，而这些站点有一部分用的是同一套
「才立方就业」系统，服务端渲染、可直接解析。

系统特征（三个接口就能覆盖）：

```
检索：/search/list?type=1&keyword=X     职位信息（需 X-Requested-With 头才返回列表片段）
      /search/list?type=4&keyword=X     招聘公告
详情：/job/view/id/{id}                  薪资 | 城市 | 类型 | 学历 + 招聘人数/需求专业/职位详情
      /campus/view/id/{id}               公告正文，常带「序号|职位|薪资|城市|学历|专业」表格
```

#### 自动选校（按你的学校与专业）

**默认不需要手工配置**，系统按三级优先自动选校，并用 `maxHosts`（默认 4）控制总量：

1. **本校** —— 从简历里识别学校名，自动探测它的就业网：
   内置 **90+ 所**高校的域名缩写表，依次尝试
   `job.{abbr}.edu.cn` / `myjob.` / `jy.` / `career.` / `scc.` / `{abbr}.91wllm.cn` / `jyzx.` 七种域名模式。
   探测结果**含否定结果**都会缓存到 `data/university-hosts.json`（带版本号，逻辑变更即失效），
   阴性结果 7 天内不重试，不会每次跑都空等。
2. **专业相关院校** —— 按简历专业挑院校类型：
   计算机 / 软件 / 电子 / 通信等 → 理工类；会计 / 金融 / 审计等 → 财经类；教育 / 中文等 → 师范类。
   每种专业都带**综合类兜底**（学科覆盖广，任何专业都能找到对口岗位）。
   理工类院校就业网的 IT 岗位密度明显更高，这一层能显著提高命中率。
3. **其余已收录院校** —— 补足到 `maxHosts`（默认 4）所。

实测选校日志长这样：

```
专业「计算机科学与技术」→ 优先 it 类院校就业网 3 所
高校就业网：检索 西安电子科技大学、东北大学秦皇岛分校、大连海事大学、厦门大学｜4 所有数据，列表 218 条，抓详情 12 条，得到 12 个岗位
```

某一类专业暂无对口院校时会明说并回退，不会静默取错：

```
专业「会计学」暂无 finance 类院校收录，回退到综合类院校
```

#### 加自己学校的就业网

把地址填进 `config.json`，它会**优先于**自动选校结果被使用：

```json
"sources": {
  "university": {
    "enabled": true,
    "maxHosts": 4,
    "hosts": [{ "name": "XX大学", "host": "https://job.xx.edu.cn" }]
  }
}
```

怎么判断地址对不对：在浏览器开发者工具里看该站点检索接口能否返回列表片段 ——
`/search/list?type=1&keyword=Java` 有 HTML 条目就可用（直接访问可能是空白页，因为需要 `X-Requested-With` 头）。

**踩过的坑**：

① 公告页的页脚也有 `<table>`（联系方式/电话/传真），一开始被当成职位表，产出「电话：0411-84724185」这种假岗位。现在要求职位行**必须带序号列**，表头行和页脚行都会被挡掉。

② 校名匹配不能用子串。`'西安电子科技大学'.includes('电子科技大学')` 为真，`'东北大学秦皇岛分校'.includes('东北大学')` 也为真 —— 但这是**四所完全不同的学校**，就业网也各不相同。早期版本用了双向 `includes`，导致成都「电子科技大学」的学生会被判定成本校是西安电子科技大学，并把错误的地址写进缓存。现在改为**规范化（去校区/括号/空白）后精确比对**。

③ 探测「能不能用」必须真的跑一遍解析器。早期只看页面里有没有 `view/id` 和 `<li`，结果把四川大学 `jy.scu.edu.cn` 误判为可用 —— 它的 `/search/list` 根本不存在，直接返回了首页 HTML（127KB），里面恰好含这两样东西。现在 `probeHost` 会直接调用真正的解析函数并要求解析出 ≥3 条，且拒绝整页 HTML。

④ 缓存要带版本号。上面 ② 的错误结论一旦写进 `data/university-hosts.json` 就会被一直复用，改好逻辑也不生效。现在缓存条目带 `v` 字段，版本不符一律丢弃重探。

#### 关于牛客校招

`https://www.nowcoder.com/jobs/school/jobs` 的 SSR 内嵌 `__INITIAL_STATE__`，每个岗位带：

```
graduationYear: "2027届"                                    ← 届别（最关键的字段）
recommendInternCompany.companyName: "美团"                   ← 公司名
jobKeys: "后端,软件工程,计算机组成原理"                        ← 技能
ext.requirements: 完整 JD 正文
deliverBegin / deliverEnd: 投递窗口
salaryMin/Max/Month, eduLevel: 薪资与学历
```

**局限**：该页只服务端渲染固定 20 条，检索接口需要登录（已实测 `/api/sparta/*` 与 `/u/job/*` 均不可用），
所以它的定位是**高质量补充源**而不是主力——拿到多少算多少，靠届别字段做精准筛选。

顺带抓取的**校招日程**（`/school/schedule`）给的是公司维度的网申窗口，
例如「小红书 | 27届秋招 | 网申至 2026-11-15」，对「现在还能投哪些」这个问题非常直接。
它会以「校招日程」标记出现在结果里，与具体岗位区分开。

`eduLevel` 编码（5000→本科、6000→硕士）是把编码与 JD 正文里的学历要求逐条对照后确认的，不是猜的。

#### 关于微信公众号通道

企业校招公告基本都发在公众号上，招聘网站往往滞后或不收录，所以这条通道的独家价值很高。
实现走的是**公开通道**，全程不需要登录微信：

1. **检索**：`weixin.sogou.com` 按关键词搜文章，拿到标题、公众号名、发布日期、摘要与加密跳转链接；
2. **还原真实地址**：搜狗的 `/link?url=` 不跟随重定向（会撞上 antispider），而是读取它返回的
   JS 片段把真实 `mp.weixin.qq.com` 地址拼接出来 —— 这一步必须复用搜索时的 cookie 会话，否则会被判定为爬虫；
3. **抓正文**：取 `js_content` 节点。注意必须做**标签配平扫描**，用 `<div id="js_content">([\s\S]*?)</div>`
   这类非贪婪正则会正文里的第一个嵌套 `</div>` 截断，只能抓到几百字的页头；
4. **抽岗位**：公众号文章是散文体，一篇可能是单公司公告，也可能是「9月校招信息汇编」这种多公司合集，
   还有可能只是经验分享。所以交给 DeepSeek 判断体裁并逐岗位抽取（公司/岗位/城市/学历/经验/批次/截止时间/投递方式）。

**为什么不让它登录你的微信**：个人微信自动化违反腾讯服务条款，且微信对自动化行为检测极严，
**极易导致账号被封**。而上面这条公开通道已验证可用，能拿到真实公告，没必要拿你的账号去冒险。

实测效果（示例简历：2026 届 Java 后端）：

```
40 篇公告 → 按相关性抓取 10 篇正文 → LLM 抽取 5 篇命中招聘信息 → 25 个岗位 → 城市过滤后 17 个并入岗位池
最终排名第 1：研发工程师 @ 华夏银行华银数字科技（北京）  90 分「高度匹配」
             命中 Java / Spring Boot / Spring Cloud / MyBatis-Plus / MySQL
```

这个岗位在智联和实习僧上都没搜到。

**排序做了哪些取舍**：公众号里混着大量地方招聘号（「XX汇博」「XX人才网」），标题被「急聘」「包住」「今日招聘」
刷满，内容却是本地社招，对没毕业的学生价值很低。因此相关性评分按
**岗位词 > 技能词 > 通用校招词** 分层加权，并对「外地地方号」「社招特征词」「过期公告（>15 个月）」做降权。
经过调优，前 10 篇待抓取文章从「全是重庆后端社招」变成了「北京 Java 岗 + 银行/央企校招」。

**已知限制**：

- 微信公众号有大量**纯图片海报**式公告（正文只有几十字、图十几张）。这类文章 LLM 读不出内容，
  会退化为「公告线索」保留标题与链接，不会产出具体岗位；
- 搜狗微信接口有反爬，触发时会打印告警并跳过剩余文章，**已抓到的结果不受影响**；
- 搜狗只支持按关键词检索，无法按城市过滤，城市偏好只能在排序阶段起作用。

#### 关于实习僧的标题「字体混淆」

实习僧会用一套**每次请求随机生成的图标字体**渲染岗位标题，抓到的数据里是私有区码点。例如：

```
&#xe26c&#xe8fc&#xec1f&#xe8fc后&#xef0f开发   →   Java后端开发
```

本项目通过**已知明文反推映射表**来还原它：

1. 详情页的 `<title>` 是明文（如 `Java后端开发实习招聘-中财进宝实习生招聘-实习僧`）；
2. 混淆是「一码点对一字符」的等长替换，因此一对「混淆↔明文」就能反推出若干字符；
3. 贪心挑选能覆盖最多未知字符的样本，抓 4–6 个详情页即可还原出映射表；
4. 用映射表一次性解码同批次全部标题，并把映射表缓存到 `data/font-map.json`，后续运行几乎零成本。

实测效果：首次运行用 8 个样本即可完整还原约 70% 的标题（如 `Java开发实习生-【风控研发】`、`服务端研发工程师（Golang）`），映射表缓存在 `data/font-map.json`；再次运行时直接复用缓存，完整还原率提升到 **130/179 ≈ 73%**，且样本抓取量自动减少。少数未覆盖的字符以 `□` 标出，完全无法还原的岗位会回退用检索关键词占位，并在界面和 CSV 中标记「标题待确认」。

> 已用 5 个不同关键词 / 城市 / 页码的页面交叉验证：映射表**零冲突**，说明该字体映射是全局稳定的，可以安全跨页复用。

接入后可以检索 BOSS直聘、牛客网、应届生求职网、前程无忧、猎聘、拉勾等**所有**招聘站点的公开页面，以及企业官网校招公告。

## 配置说明

`config.json` 全部字段：

```json
{
  "deepseek": {
    "apiKey": "",                        // DeepSeek 密钥，留空则读环境变量/DSH 凭据
    "baseUrl": "https://api.deepseek.com",
    "model": "deepseek-chat",            // 也可用 deepseek-reasoner（更慢更贵）
    "concurrency": 4,                    // LLM 并发数
    "timeoutMs": 120000,
    "allowUserKey": true                 // 允许访客自带 Key（公网多用户建议开启）
  },
  "search": {
    "provider": "auto",                  // auto | tavily | bocha | serper | none
    "tavilyApiKey": "",
    "serperApiKey": "",
    "bochaApiKey": ""
  },
  "sources": {
    "zhaopin":    { "enabled": true, "maxPages": 3, "delayMs": 600 },
    "shixiseng":  { "enabled": true, "maxPages": 3, "delayMs": 800, "titleRepairSamples": 8 },
    "searchApi":  { "enabled": true, "maxQueries": 6, "resultsPerQuery": 10 },
    "wechat": {
      "enabled": true,
      "maxPages": 1,                     // 搜狗每页 10 条，翻页过多易触发反爬
      "maxFetch": 10,                    // 最多解析链接并抓正文的篇数
      "maxExpand": 6,                    // 最多交给 LLM 抽取岗位的篇数（每篇约 2500 token）
      "maxQueries": 4,                   // 公众号检索词条数
      "delayMs": 1200                    // 搜狗对频率敏感，不建议调低于 800
    },
    "nowcoder": { "enabled": true, "includeSchedule": true, "maxSchedule": 6 },
    "university": {
      "enabled": true,
      "maxHosts": 4,                     // 最多用几所学校的就业网
      "maxPerKeyword": 12,               // 每校每关键词最多取几条列表
      "maxDetail": 12,                   // 每轮最多抓几个详情页
      "delayMs": 900,
      "hosts": []                        // 留空=按简历的学校/专业自动选校；
                                         // 填 [{"name":"XX大学","host":"https://job.xx.edu.cn"}] 则优先用它
    },
    "maxCities": 2,                      // 覆盖几个期望城市
    "secondaryCityKeywords": 2           // 非首选城市每个跑几个关键词
  },
  "match": {
    "shortlistSize": 60,                 // 规则预筛后进入精排的岗位数

    "scoreBatchSize": 8,                 // 每次 LLM 调用评估几个岗位
    "minScore": 40                       // 过滤掉低于此分数的岗位（设为 0 则全部保留）
  },
  "filters": {
    "graduationYear": "2027",            // 目标届别，留空则不过滤
    "includeInternship": false,          // 是否保留实习岗
    "strict": true,                      // true=硬过滤；false=只标记不剔除
    "yearQueryCount": 3,                 // 用几个「届别」检索词去招聘站搜校招岗
    "cities": []                         // null=从简历推断；[]=不限城市；["北京"]=指定
  },
  "auth": {
    "mode": "password",                  // password | none（none 仅限本地，公网会被拒绝启动）
    "passwordHash": "",                  // 也可用 npm run hash-password 生成后填这里
    "sessionTtlHours": 168,              // 登录有效期（7 天）
    "maxLoginFails": 5,                  // 连续失败几次锁定
    "lockMinutes": 15                    // 锁定时长
  },
  "limits": {
    "maxConcurrent": 2,                  // 同时执行的任务数
    "maxQueue": 8,                       // 排队上限，超出直接拒绝
    "dailyGlobal": 100,                  // 全站每日检索次数
    "dailyPerIp": 10,                    // 单 IP 每日次数
    "perIpCooldownMs": 30000             // 同一 IP 两次检索的最小间隔
  },
  "server": {
    "port": 3210,
    "host": "127.0.0.1",                 // 公网部署改为 0.0.0.0
    "trustProxy": false,                 // 在 nginx/Caddy 之后置为 true

  }

```

### 调优建议

| 想要 | 调整 |
| --- | --- |
| 更快出结果 | `zhaopin.maxPages` / `shixiseng.maxPages` 降到 1–2，`enrichTopN` 降到 0–5 |
| 覆盖更广 | 提高 `maxPages` 与 `searchApi.maxQueries`，接入搜索 API |
| 只看高质量岗位 | `minScore` 设为 60 或 70 |
| **结果太少** | 提高 `match.shortlistSize`（默认 150），或打开 `filters.includeInternship` |
| 省 token | `shortlistSize` 降到 60，`scoreBatchSize` 提到 10 |
| 公网省额度 | `allowUserKey: true` + 调小 `limits.dailyPerIp` |

## 匹配分怎么算

分两阶段，规则保底、LLM 精排：

**第一阶段 · 规则预筛**（全部岗位，0–100）

| 维度 | 权重 | 判定方式 |
| --- | --- | --- |
| 岗位方向 | 22 | 岗位标题（或描述）是否命中**岗位族词表** |
| 技能 / 岗位要求 | 45 | 技能、标签、JD 正文中命中的简历关键词比例 |
| 城市 | 15 | 是否在期望城市内（不限城市时给满分，不因城市丢分） |
| 学历与专业适配 | 18 | 学历是否达标、岗位的专业要求是否与你的专业相符、经验要求是否超出应届身份 |

> **权重为什么是这么分的**：早期版本「岗位方向」占 35 分且要求标题**逐字命中**简历里写的目标岗位，
> 结果标题写作「服务端研发」「平台开发」「基础架构」但要求高度吻合的岗位，方向分直接是 0，
> 根本进不了短名单。现在改为匹配由「专业 + 技能」推导出的**岗位族词表**（约 20 个词），方向分降到 22，
> 技能/要求匹配提到 45 —— 因为要判断的是「这份简历能不能胜任」，而不是「标题叫不叫得一样」。

**岗位族词表怎么来的**：从简历的技能栈推导同类岗位的各种叫法。例如 Java 后端方向会推出
`后端开发 / Java开发 / 服务端开发 / 服务端研发 / 后端研发 / 软件开发 / 研发工程师 / 微服务开发 / 中间件开发 / 基础架构 / 平台开发 / 应用开发 / 系统开发`，
这些词既用于**检索**（扩大召回），也用于**打分**（判断方向是否沾边）。

**第二阶段 · DeepSeek 精排**（入围岗位）

把求职者画像与岗位卡（含完整 JD）批量交给 DeepSeek，按统一标准重新打分，并给出中文理由与差距。LLM 调用失败时自动回退到规则分，不会中断流程。

## 常见问题

**Q：提示「未配置 DeepSeek Key」怎么办？**
A：按[第 3 步](#3-配置-deepseek-key)配置。不配置也能跑，但会退化为内置词表的离线规则模式，关键词识别和匹配理由质量都会下降。

**Q：为什么搜不到 BOSS直聘 的岗位？**
A：BOSS直聘的列表页是纯前端渲染且反爬严格，无法直连抓取。要覆盖它需要接入[全网搜索 API](#开启全网搜索通道)。

**Q：为什么没检索到我学校的就业网？**
A：先看运行时日志里有没有「正在探测「XX大学」的就业网…」。有的话说明探测过了但没命中 ——
全国高校就业网系统很杂，实测 400 次探测只有少数几所和本工具适配的系统一致，
其余的要么是自研平台、要么需要登录鉴权。可以自己把地址加进
`config.json` 的 `sources.university.hosts`，它会优先被使用（判断方法见[加自己学校的就业网](#加自己学校的就业网)）。
不支持的学校不会影响其他数据源，程序会安静地回落到按专业匹配的院校。

**Q：`data/university-hosts.json` 是什么？**
A：高校就业网的探测缓存。命中的记录会一直复用；没命中的也记下来，7 天内不再重试，
避免每次检索都空等一遍探测。想看某所学校到底能不能用，删掉这个文件再跑一次就能重探。

**Q：上传 PDF 后提示提取不到文字？**
A：你的 PDF 可能是扫描件（本质是图片）。请改用文字版 PDF，或直接把简历内容粘贴到输入框。

**Q：跑了很久没结果？**
A：首次运行要抓取多个关键词 × 多页岗位，并抓取入围岗位的完整 JD，正常需要 40–90 秒。想更快就把 `maxPages` 和 `enrichTopN` 调小。

**Q：能搜非技术岗吗？**
A：可以。系统不限定岗位类型，产品、运营、设计、财务、人力等岗位同样支持，只要简历里的技能与经历能被提取成关键词。

**Q：端口被占用？**
A：换个端口：`set PORT=3211 && npm start`（Windows）或 `PORT=3211 npm start`（macOS/Linux），也可改 `config.json` 里的 `server.port`。

**Q：结果能保存下来吗？**
A：每次检索都会自动存到 `data/runs/`，界面上点「历史记录」可以随时回看和导出。

**Q：怎么让别人也能用？**
A：见 [`deploy/部署指南.md`](deploy/部署指南.md)。最短路径是 `cp .env.example .env` 填好密码与密钥，然后 `docker compose up -d --build`，再配好 HTTPS 反代。

**Q：启动时报「拒绝启动：监听地址为 0.0.0.0 但没有配置登录口令」？**
A：这是有意的保护。公开暴露却无鉴权，等于把 DeepSeek 额度和抓取能力免费送人。按提示设置 `AUTH_PASSWORD` 即可；只想本机用就把 `host` 改回 `127.0.0.1`。

**Q：部署后前端一直卡在「正在启动…」，最后一次性刷出来？**
A：反向代理的响应缓冲没关。nginx 需要对 `/api/analyze` 设 `proxy_buffering off;`，Caddy 用 `flush_interval -1`。`deploy/` 里的配置已经处理好了。

**Q：所有访客被算成同一个 IP，限流失效？**
A：在反代之后没设 `TRUST_PROXY=1`。反过来，**如果没在反代后面却开了它，伪造 `X-Forwarded-For` 就能绕过限流**，所以别乱开。

**Q：担心公开后额度被刷爆？**
A：三层防护：并发闸门、每日配额（全站 + 单 IP，落盘不因重启重置）、以及让访客自带 Key（默认开启）。默认配置下最坏情况是每天 100 次检索，约 ¥5–15。

**Q：忘了站点密码？**
A：改 `.env` 里的 `AUTH_PASSWORD` 后重启即可。

**Q：桌面版双击没反应 / 打不开？**
A：先看菜单「帮助 → 关于」里的数据目录是否可写；若曾清理过该目录，删掉 `%APPDATA%\ResumeJobRadar` 让应用重建即可。命令行运行 `简历岗位雷达.exe --self-test` 可打印 15 项自检结果，快速定位是哪一步出问题。

**Q：桌面版 318MB 是不是太大了？**
A：体积几乎全部来自 Electron 内置的 Chromium 内核（exe 本体就 200MB），这是所有 Electron 应用的共同特点。已经做的精简：语言包从 55 个砍到 4 个（省 42MB）、排除 36MB 的 PDF 渲染库。如果只想要小体积，用网页版（`npm start`，浏览器访问，仅几十 KB 代码）。

**Q：桌面版和网页版能同时用吗？**
A：可以。桌面版监听随机端口、数据在 `%APPDATA%\ResumeJobRadar`；网页版监听 3210、数据在项目 `data/`。两者互不干扰。

**Q：桌面版会不会把我的 Key 传出去？**
A：不会。Key 只存在你自己的机器上（浏览器 localStorage），只发往本机内置服务，再直连 DeepSeek 官方接口。打包产物里已明确排除 `config.json` 与 `.env`，构建时会自动校验。

**Q：我只要 2027 届的校招，怎么设置？**
A：界面上把「目标届别」选成 2027 届、取消勾选「含实习岗」即可；也可以在 `config.json` 的 `filters.graduationYear` 里固化。详见[届别过滤](#只要某一届的校招届别过滤)。

**Q：设了届别之后结果很少（只有十几条）？**
A：这是正常的。校招岗位总量本就远少于社招和实习——实测 1135 条采集结果里，符合「2027 届 + 非实习」的只有 76 条，精排后 13 条。**宁缺毋滥**正是这个过滤器的目的。想要更多可以：打开「含实习岗」、增加期望城市、或调高 `filters.yearQueryCount`（会变慢）。

**Q：为什么打开「含实习岗」后，结果几乎全是实习？**
A：实习僧的岗位量比校招岗大一个数量级。两者混排时实习会占满列表，所以默认不含实习。这也是「校招」和「实习」建议分开看的原因。

**Q：岗位没写届别，会被误杀吗？**
A：不会。明确是校招（有「校招/校园招聘/秋招/应届」等字样）但没写具体届别的岗位会**保留**；只有「完全没有任何校招线索、也没写经验要求」的岗位才会在严格模式下剔除。想在结果里看到被剔除的原因，看运行时日志里的「剔除原因」统计。

## 开发环境已知坑

这些是实际调试时踩出来的，写在这里以免重复排查。**前两条尤其误导**——它们会让人得出完全错误的结论。

### ① 本机装了透明代理时，`web_fetch` 工具会拒绝访问 GitHub

代理的 fake-IP 模式会把域名统一解析到 **`198.18.x.x`**（RFC 保留的基准测试网段）。`web_fetch` 的 SSRF 防护看到非公网 IP 就拒绝，报「URL hostname resolves to a non-public IP address」。

**但网络其实是通的。** 诊断方法：

```powershell
node -e "fetch('https://github.com/',{method:'HEAD'}).then(r=>console.log(r.status))"
```

用 Node 的 `fetch` 直连能拿到 200，说明问题在工具层不在网络层。

### ② `github.com` 网页版不通，`api.github.com` 却正常

实测（同一环境下同时测）：

```
❌ github.com          UND_ERR_CONNECT_TIMEOUT（10 秒超时）
✅ api.github.com      HTTP 200  342ms
✅ gitee.com           HTTP 200
```

所以**抓 HTML 页面这条路走不通，只能走 API**。取 README 用 `GET /repos/{owner}/{repo}/contents/README.md`（返回 base64），因为 `raw.githubusercontent.com` 同样不通。

### ③ GitHub 搜索限额是「10 次/分钟」，且逐查询延迟不等于全局限速

```
core    60 次/小时   ← /repos、/git/trees
search  10 次/分钟   ← /search/repositories
```

**踩坑经过**：按「每个查询等 7 秒」跑 18 次搜索，1.5 分钟跑完 → 撞上 10 次/分钟，后半段全部 403。

**正确做法是全局节流**：维护一个 `lastCall` 时间戳，保证任意两次搜索间隔 ≥ 6.3 秒（不带 Token）或 ≥ 2.2 秒（带 Token，30 次/分钟）。

带 Token 的收益很大，而且**不需要任何 scope**（不勾权限的经典 Token 同样有 5000/小时，且只读公开信息，泄漏了也改不了东西）：

```powershell
$env:GITHUB_TOKEN = "ghp_xxxx"
```

配额查询：`GET /rate_limit`（这个接口**不消耗配额**）。

### ④ 中文关键词的 GitHub star 排序不可信

- 按语言/文件数过滤（这类仓库基本是纯 HTML 或空仓库）

## 合规与使用边界

- 本工具仅读取招聘网站**公开可访问**的页面内容，用于个人求职信息检索。
- 不模拟登录、不绕过验证码、不破解加密接口、不采集个人隐私信息。
- 内置了请求间隔（`delayMs`）与并发限制，避免对目标站点造成压力。**请勿把 `delayMs` 调至 0 或大幅提高并发**，那既容易被封也可能违反站点条款。
- 抓取到的岗位信息版权归原网站及发布企业所有，请以原始页面为准；本工具仅做检索与排序，不存储、不转售岗位数据。
- 请遵守目标网站的服务条款与 robots 协议，将本工具用于个人求职用途。

## 技术栈

- **运行时**：Node.js（原生 ESM，尽量零依赖）
- **PDF 解析**：`pdfjs-dist`
- **DOCX 解析**：自研 ZIP 中央目录解析 + `zlib.inflateRawSync`（零依赖）
- **LLM**：DeepSeek（OpenAI 兼容接口，JSON 模式）
- **前端**：原生 HTML / CSS / JS，无构建步骤
- **服务端**：Node 原生 `http`，NDJSON 流式推送进度
