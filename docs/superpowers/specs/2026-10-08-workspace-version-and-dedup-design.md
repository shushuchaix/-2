## 1. 用户要求与成功标准

本轮服务于用户长期使用的本地求职工作台，改善岗位库、简历与目标的保存和管理。

已明确：

1. 目标新版本可以自定义名称。同名版本只能保存一份，允许保留多个不同名称的版本。
2. 清理范围为**所有版本的重复条目**，包括当前、停用、历史及回收站中的目标版本。
3. 岗位重复必须有合理的证据判断，不因公司或标题相似直接删除。
4. 修复“已保存的版本”中停用、删除等操作，并为每个成功操作显示可见提示。
5. 保存目录和界面分类应清楚，能找到真正使用的本地数据。

成功标准：不同名称的目标版本能独立选择和更新；同名或重复提交不会产生多份版本；所有版本的岗位列表只有一份相同岗位条目；操作状态、列表与编辑表单一致；其他版本归属、画像、原文证据、历史及投递记录完整；失败不显示成功。

同一 `jobId` 同时属于多个目标版本属于正常使用关系，不是多份岗位实体。全版本去重会合并重复实体并更新所有版本关联，不会把某个版本正常引用的岗位移除。

## 2. 已复现的问题

检查及复现使用合成内存数据，未读取日常私人正文、联网或改动用户数据。

| 问题 | 根因 | 处理 |
| --- | --- | --- |
| 停用后保存又变成启用 | 页面只刷新历史列表，编辑表单仍持有旧 `enabled:true` | 状态、编辑器、选中版本同步更新 |
| 旧目标无法停用 | PATCH 仍调用完整目标保存，旧站点或预算不符合当前配置时拒绝 | 状态操作走独立事务，校验操作及引用，不校验无关来源或模型 |
| 金额预算目标无法保存新版本 | 表单携带旧预算，但前端校验没有模型配置 | 表单使用实际只读模型配置；后端保留预算约束 |
| 删除按钮看似不可用 | 简历被目标、历史或投递引用时拒绝删除，页面未明确展示原因 | 支持移入回收站，历史引用保留；永久删除只处理无引用版本 |
| 没有目标删除功能 | 当前目标没有 DELETE 路由或服务 | 补齐版本级回收站操作 |
| 精确版本列表遗漏或混入岗位 | 入库只记录 `targetId`；查询用评价存在性代替版本归属 | 建立明确版本成员关系 |
| 无链接岗位重复入库冲突 | 弱身份同键未判相同，固定冲突后缀导致第三次碰撞 | 相同完整内容入库幂等；有区别的记录使用完整内容指纹区分 |
| 同一链接下不同岗位被当作相同 | 现有身份算法没有完整检查标题、批次、学历等 | 入库及清理使用保守身份规则，列表/活动链接不作为详情唯一标识 |
| 分类混合维度 | 推荐、资格、公告混在一个选项中，部分类别缺失 | 分开各筛选维度 |
| 历史目录菜单打开错误位置 | 打开旧 `runs/`，当前快照实际在 `runs-v2/` | 修复当前历史入口，旧版历史单独标记 |
| 成功反馈可能不在视口内 | 提示位于页面顶部，长列表操作后可能看不到 | 操作行提示及全局可见通知 |

## 3. 架构取舍

采用现有 Node/Electron、JSON 工作区和原子事务，新增明确的版本元数据、版本岗位成员与岗位重定向。

| 方案 | 优点 | 代价 | 选择 |
| --- | --- | --- | --- |
| 单账本、版本关联、保守去重 | 保持原子一致性，事实只存一份，各版本保留评价和人工记录 | 需要补齐版本关联和旧 ID 解析 | 本轮采用 |
| 每个版本独立目录及岗位文件 | 文件位置直观 | 相同事实重复保存，跨文件删除和恢复难以保持引用一致 | 本轮不采用 |
| 同时迁移数据库和界面框架 | 可支持更大数据量 | 存储、备份、入口及打包全部变化 | 独立后续需求 |

这次整理目录和缓存，不搬迁权威工作区文件，不把开发环境、其他工作树与正式桌面数据自动合并。

## 4. 版本管理

### 4.1 名称与唯一性

- 目标版本名称必填，1–60 个字符。名称只作为显示元数据，不作为文件路径。
- 唯一键使用 NFKC、首尾去空白、连续空白折叠、英文大小写统一；保留有意义的内部空格与标点。
- 目标名称在当前工作区全部目标版本中唯一，包括停用及回收站版本。恢复或创建同名版本时给出已占用提示及前往查看入口。
- 简历版本提供可选自定义名称；未填写时按创建日期与稳定版本标识生成可区分名称。简历与目标各自使用独立名称空间。
- 旧目标没有名称时一次性生成“岗位方向 · v序号 · 短ID”形式的唯一名称，旧引用 ID 保持不变。
- 重命名已有版本允许保留自身名称；名称冲突在持有工作区锁时检查，防止并发重复创建。

### 4.2 版本与操作

- 配置、画像事实和版本 ID 保持不可变。新建版本要求新名称，并形成一个新的配置版本。
- 重命名、启用、停用及回收站状态属于可变管理元数据，不生成配置版本，不改变历史任务快照。
- 所有已保存版本列表分为简历、目标两组，再按正常/停用/回收站筛选。目标不再只显示每组最新版本。
- 同一版本在列表中只出现一次。保存返回的数据按 `revisionId` 替换或插入，不无条件追加。
- 同一提交标识且相同内容的网络重试返回首次结果，标识相同但内容不同则拒绝。不同提交占用同名时返回名称冲突提示，不创建额外版本；重命名为自身原名称返回“名称未变化”。
- 已有版本进入编辑器时显示“新建版本”模式，新名称留空；只有另存新名称才产生配置版本。重命名提供独立操作。
- 修改启停后同时更新历史行、表单状态、工作台选中状态和可更新状态。停用版本仍可浏览岗位，禁止发起新的采集。
- 停用不强制终止已开始的任务。回收站操作在该版本有活动任务时拒绝并说明需先等待或取消任务。

### 4.3 删除与引用

- 默认“删除”操作将版本移入回收站，给出“已移入回收站，可恢复”提示，从正常新建/更新选项中移除。
- 被引用的画像或目标仍能移入回收站，既有历史、评价及投递可读取；新建目标不能选择回收站画像，新任务不能选择回收站目标。
- 画像在回收站时，引用它的既有目标仍可浏览，但不能发起新采集或重评分；目标与工作台显示“关联简历在回收站，请先恢复或创建目标新版本”。恢复画像后重新计算可运行状态，不自动生成或改写目标版本。
- 画像移入回收站的活动检查包括所有间接引用它的采集和独立重评分操作；有活动操作时拒绝并明确说明。目标启停与回收站操作同样检查相关操作，历史只读访问不受阻。
- 回收站可恢复，恢复继续使用原 ID 和原名称。
- 永久删除仅允许没有任务、目标、评价、岗位成员、投递等引用的版本。提示列出引用类别及数量；不允许隐式级联删除人工记录或历史。
- 版本序号保留已分配的最大值，删除后不会复用旧 ID。
- API 验证路径父 ID 与版本 ID 的一致性，不接受通过另一资源路径操作某版本。

## 5. 全部版本的岗位归属

新增 `targetRevisionId → jobId` 的明确成员集合，保存版本内首次发现、最近发现、来源运行 ID、对应观察 ID 和事实哈希。

入库使用任务冻结的目标版本登记成员，同一岗位在每个版本中最多一条成员。尚未评价的岗位仍属于采集它的版本。

旧数据回填：

1. 优先用任务的目标快照及观察记录回填。
2. 任务评价 ID 和独立重评分的目标版本作为补充可验证关联。
3. 只有目标级首次发现、无法确定版本的记录归入“历史未归属”，保留待查看，不猜测分配到所有版本。

回填事务幂等，回填后同时验证版本、岗位、来源运行引用。查询同时填写目标 ID 与版本 ID 时要求版本确实属于目标，只使用该版本的成员集合。

成员来源区分采集任务与手工导入操作。手工导入允许 `runId:null` 和独立来源操作标识；旧观察中的 `import-UUID` 保留，不因没有 `runs` 节点而视为损坏。没有选择目标版本的手工导入归入“历史未归属”，不能自动加入所有版本。

精确版本的列表、详情和重评分使用该成员指向的岗位事实。全局岗位库使用最新已确认的事实。详情同时展示版本依据与当前来源情况，不能把旧版本的分数配上其他版本的新学历或正文。版本依据无法回填时明确显示“历史依据缺失，需核实”，不悄悄替换成全局正文。

新评价保存观察 ID 和独立事实内容哈希，哈希包含实际岗位内容与资格条件，排除岗位内部 ID、来源内部 ID、采集时间等身份元数据。选择当前评价时必须同时匹配目标版本和当前版本事实；缓存仍保留原有画像、目标、提示词、规则及模型版本约束。旧评价 `jdHash` 不改写，用旧评价的原 `jobId` 与候选观察内容按旧算法重建校验；无法可靠对应时只展示为带原依据的历史评价，并提示需要重新评分，不借用最新一条分数。

## 6. 重复判断

判断器输出 `confirmed / possible / distinct`、固定理由代码和用于本地比较的字段。人工“关联”只表示用户建立关系，不自动等于可以删除。

### 6.1 冲突先行

任一已知条件冲突即保留独立记录：

- 具体岗位、招聘公告、公司招聘窗口种类不同。
- 公司主体、分公司/子公司或岗位标题明确不同。
- 城市集合不同，不能因存在一个相同城市就合并；未知城市不当作相同城市的证据。
- 校招、实习、社招类型、毕业届别、招聘批次或年份不同。
- 职级、学历、经验、必需证书或明确工作方式不同。
- 相同来源与身份作用域下明确岗位编号不同。
- 来源 ID 被跨年度复用且存在批次/要求变化，不作为同一实体处理。

发布日期、截止日期和薪资差异可能是更新，也可能是新批次。没有同一招聘机会的强证据时仅列疑似；不通过取最新值抹掉差异。

岗位编号的权威性由可信适配器的实际岗位来源确定。系统为导入生成的随机 UUID、任务内部 ID 和模型生成 ID 不属于权威招聘编号，不产生“不同岗位编号”冲突，也不进入业务内容指纹。手工填写的编号只作为线索，不能自行提升为可信权威 ID。

### 6.2 可以清理的重复

无上述冲突且满足下列之一：

1. 同一可信来源、身份作用域、岗位 ID，并且公司、标题与招聘批次证据一致。
2. 同一个可确认属于具体岗位的详情/申请 URL，公司、标题及已知岗位条件一致。公司首页、列表、公告集合、活动通用申请页不适用。
3. 没有权威 ID 时，完整有效原文和公司、标题、种类、城市、类型、批次及要求一致。只有空正文、短描述或通用模板不适用。
4. 无链接手工记录的完整输入内容一致，只有采集时间等运行元数据不同；重复导入沿用同一记录，不创造第二个实体。

URL 只去掉已知追踪参数，保留岗位编号、未知参数、签名和 SPA 路由。标题只做 Unicode 与空白规范化，保留职级、班次、实习等区别。公司名称不去掉分支主体。

### 6.3 疑似与分组

公司和标题相似、关键条件缺失、正文仅有模板或发布日期含义不清时保留为疑似，提供逐项比较。疑似不会进入默认可清理列表。

分组不使用相似关系的简单传递闭包。每个拟合并成员必须与主记录及组内其余成员满足确定重复条件，不接受“A像B、B像C，所以A等于C”。

## 7. 全版本清理事务

### 7.1 预览与确认

- 岗位库提供“清理所有版本重复岗位”，服务端扫描完整工作区，包含停用、历史和回收站版本，不限当前页面或筛选结果。
- 预览显示范围、确认重复组数、重复实体数、涉及版本数、疑似数量、受人工记录保护数量，以及每组保留项、删除项和依据。
- 预览返回工作区修订号和计划摘要。提交时持锁重新计算；预览期间岗位或人工记录变化则提示刷新，不执行过期清理。
- 实际清理前生成可恢复业务备份。默认选中确认重复且无人工冲突的组，疑似只能查看比较。

### 7.2 保留与合并

主记录选择顺序：有人工记录者优先，其次可信来源、信息完整度、最早稳定记录；相同条件按稳定 ID 决定，确保重复执行不改变主记录。

人工记录包括投递状态、备注、日期、简历选择、事件、跟进或其他手动修改，也包括通过 `legacyJobIds` 间接引用成员的旧版歧义投递。组内多于一条有人工记录时默认保护整组，即使状态看似相同也不自动覆盖；预览说明需要人工处理。只有一条人工记录时保留该岗位和原记录全部内容。

在一次原子事务中：

1. 汇总主岗位的非冲突事实、来源引用、身份别名、首次/最近发现；原文证据及各来源观察保留。
2. 所有版本成员改为主岗位 ID，同一版本的多条成员归并为一条，保留版本内发现时间和来源运行记录。
3. 从当前岗位事实集合移除被合并实体，记录旧 ID 到主 ID 的重定向及清理操作元数据。
4. 不改写不可变评价、来源观察、历史运行快照和它们的哈希。查询通过旧 ID 重定向聚合历史；按目标版本及可验证的版本事实选取评价，不能跨版本或跨事实借分。
5. 投递更新、岗位详情、导出、来源身份解析、解除关联、重评分等入口统一解析旧 ID，避免删除后出现“岗位不存在”。历史快照回放仍使用当时事实。旧版歧义投递查询和详情候选同样解析并去重主 ID；候选最终只有一个时展示确定关联，但原人工字段、原候选标识及事件留存，不隐式丢弃投递记录。
6. 新入库解析既有身份别名和重定向，防止下次更新重新产生同一重复实体。重定向无环、目标存在，解析有界。

返回确认组数、删除实体数、消除版本内条目数、受影响版本数、疑似数量、保护数量及备份结果。成功提示准确区分“删除了多少份重复实体”和“多少个版本中的条目被归并”。

该操作清理当前工作区所有版本的重复实体，不删除不同版本的评价和历史证据，因此磁盘总量不会按删除条目数等比例下降。

### 7.3 恢复与备份兼容

新增元数据、成员、重定向及清理操作记录包含在完整业务备份中，凭据仍不包含。旧备份恢复后会补齐管理元数据及版本成员，并重新执行同一保守身份规则；不自动运行全局删除。

先校验原备份哈希，再规范化缺失的新字段并完整替换工作区；不能用局部对象覆盖遗留恢复前的重定向、成员或回收站字段。恢复后校验所有引用，新旧备份都不得留下悬空重定向。

恢复完整备份按现有流程先备份当前工作区，验证完整性，再恢复；用户可用清理前备份整体回退。清理不提供可能覆盖后续投递修改的单组自动撤销。

## 8. 分类与反馈

岗位库将下列维度独立呈现，筛选可组合且分页总数基于去重后的全部匹配项：

| 维度 | 分类 |
| --- | --- |
| 目标版本 | 所有正常/停用/历史版本、全部、历史未归属；回收站版本从回收站进入 |
| 记录类型 | 具体岗位、招聘公告、公司招聘窗口、全部 |
| 推荐结果 | 优先推荐、可以考虑、匹配较低、信息不足、不推荐、尚未评价 |
| 资格 | 已确认通过、待核实、不符合、全部 |
| 投递 | 现有未处理、已看过、感兴趣、已投递、面试、录用、未通过、忽略 |
| 重复情况 | 正常、疑似重复、人工记录待处理 |

默认进入所选目标版本的具体岗位；公告和公司窗口单独查看。版本选项展示自定义名称、简历关联及启停状态，技术 ID 收入详情。全部记录模式始终可选。

保存、新建、重命名、启用、停用、移入回收站、恢复、永久删除、去重、导入、重评分、投递修改、备份、恢复、导出及打开目录均有明确成功反馈。通知位于可见区域并通过 `aria-live` 播报；行内显示操作结果。业务写入完成后才通知，读取刷新不覆盖刚发生的操作成功提示。

浏览器导出只能确认文件生成并已触发下载，提示“导出已生成，已开始下载”；不能宣称已写入用户磁盘。可确认完成本地写入的桌面操作才提示“已保存”。目录打开成功表示系统接受了打开操作，不表示修改了目录内容。

忙时禁止重复点击，失败保留输入和旧状态。错误提示含操作、准确原因及可采取的行动；结构化错误保留安全诊断编号。不会把引用保护、预算校验或目录权限错误统一显示为“保存失败”。

## 9. 保存目录

使用现有桌面数据根目录和 `RJR_DATA_DIR` 覆盖规则。设置页新增“本地数据与保存位置”，只在本地桌面展示实际路径：

```text
ResumeJobRadar/
  workspace.v2.json          # 岗位、简历、目标、人工记录的唯一事务账本
  workspace.v2.previous.json # 上一有效版本保护
  config.json               # 运行配置
  credentials.v2.json       # 系统加密凭据
  .workspace.lock           # 跨进程锁
  runs-v2/                  # 当前不可变运行历史
  backups/                  # 完整业务备份
  cache/                    # 可重建来源辅助缓存
  logs/                     # 脱敏运行日志
  runs/                     # 旧版历史，只标作兼容数据
```

初始化及路径计算集中到统一目录模块。字体映射和来源发现等已知缓存移入 `cache/`，新路径优先、旧文件作为一次性验证导入来源，不递归移动未知目录。

简历正文和画像保存在账本中；导入文件当前不作为原件永久保存，不能把旧 `uploads/` 宣称为简历原件目录。浏览器导出仍使用系统下载位置，界面不显示不存在的固定导出历史。

提供打开数据、当前历史、备份、日志、缓存目录及复制路径操作。桌面 IPC 只接受固定类别，主进程映射路径并验证窗口、主框架和本机应用来源；不接受任意绝对路径。公开 Web 不提供私人路径 API，日志不记录绝对路径。

## 10. 迁移与验证

- 不修改原始简历、画像事实、人工备注或旧快照内容，不把版本名称写进模型输入。
- 扩展现有工作区 schema 的可选管理字段；缺字段的旧工作区可读。管理字段严格验证形状、ID 引用、唯一名称和无环重定向。
- 首次补齐在工作区锁内执行，写入前创建业务备份；重复启动不重复迁移。部分失败保留旧有效数据，记录安全结果。
- 采集任务或独立重评分正在运行时不执行全局去重或永久删除；使用操作门禁防止检查后又启动竞争操作。预览可读，清理须等相关操作结束。评价保存等入口仍解析旧 ID，防止遗漏入口或跨进程竞争导致“岗位消失”。
- 单版本/跨版本岗位归属、未评价岗位、旧历史未归属、全部版本筛选和分页计数都使用合成集验证。
- 去重验证包括城市集合、届别、批次、岗位编号、学历、职级、经验、证书、同链接不同岗位、模板正文、缺失字段、链式分组以及重复入库三次。
- 人工记录保护、旧 ID 详情/投递/导出访问、各版本原文与评价分离、清理后重新采集、并发/过期预览、幂等、新旧备份恢复和无悬空映射需要回归。
- UI 使用真实点击验证保存、重名、启停、删除、恢复及清理反馈；桌面 EXE 自检补充这些流程，并验证版本名称和成功通知可见。
- 保留原模型 10 元预算和隐私规则；本轮不发起付费模型调用或自动重新采集个人招聘目标。
