# 全面日志升级说明

日期：2026-10-07，Asia/Hong_Kong。

## 目的与适用范围

用户要求日志更详细、全面，能够根据新的报错定位并修改程序。此次扩展已有本地诊断链路，让招聘更新、外部请求、模型处理、工作区存储和桌面界面的异常保留可关联的过程信息。

日志帮助区分失败发生在哪一步，不会自动修复招聘网站、模型服务或操作系统的故障。升级前缺失的信息无法追补；新记录从新版运行开始产生。

## 使用方法

1. 在工作台的对应更新任务展开「查看更新日志」，点击「刷新日志」。
2. 选择「错误与提醒」，点击「筛选日志」。先查看来源、站点、阶段／步骤、错误代码、HTTP 状态及调用位置。
3. 根据问题选择「网络」「存储」「模型」「桌面与界面」等分类；若提示中有 `d-` 开头的错误编号，可粘贴完整编号定位对应记录。
4. 点击「查看全部日志」查找任务启动、关联请求和其他软件操作；设置页也可查看全部日志。排查阶段前后的过程时，改为「全部级别」，避免只看到异常摘要。
5. 点击「导出日志」下载 `job-radar-update.log`。导出沿用当前任务范围及筛选条件；需要完整过程时，先选择全部日志、全部级别、全部分类并清空错误编号，再筛选和导出。

界面显示最近最多 200 条，摘要显示匹配总数、错误／提醒数、时间范围与保留限制。默认导出包含当前仍保留的全部匹配记录，并按时间先后排列；它不受界面的 200 条上限影响。调用导出 API 时若显式指定条数上限，文件会提示截断。

桌面菜单「文件 → 打开运行日志目录」打开当前数据目录下的 `logs/`。文件不会自动上传；用户可自行选择是否分享导出文件。

## 新增的诊断覆盖

| 范围         | 记录的过程及可用信息                                                                                                                                         |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 更新任务     | 采集计划、阶段开始／结束、来源返回、页面解析、批次入库、详情检查、公告展开、评分、取消与最终汇总；原始／有效／去重／符合资格／候选等计数，来源覆盖与预算用量 |
| 外部网络     | 请求用途、单次尝试与最终结果、排队／DNS／传输及总耗时、超时上限、HTTP 状态、响应字节数、缓存、重试间隔、重定向次数与请求预算                                 |
| 解析         | 格式、返回结构类型、固定缺失字段名、选择器是否存在、标题是否为唯一内容、文本长度和结果数；不保留正文                                                         |
| 模型         | 请求与尝试、格式降级、JSON 校验／修复、规则回退、缺失结果与调用／token 用量；不保留提示词或回复                                                              |
| 工作区与存储 | 启动、迁移、恢复、设置、备份／恢复；事务耗时和版本、锁／读／写／替换／快照等失败步骤、原始错误代码、自动重试恢复                                             |
| 应用请求     | 已知 API 路由模板、方法、状态、耗时、请求编号与关联错误；记录失败请求和成功的修改操作，避免正常轮询和日志读取反复生成日志                                    |
| 桌面与界面   | 启动环境、页面加载、preload、渲染进程异常、无响应、凭据操作失败、界面请求／事件流／运行异常                                                                  |

字段按事件是否具备相应信息出现。不存在的计数、状态或耗时不会推测填入；日志留白不能证明某步骤已经成功。

## 关联编号

| 字段                  | 用途                                                                  |
| --------------------- | --------------------------------------------------------------------- |
| `diagnosticId`        | 单条诊断的 `d-` 编号；部分错误提示会返回这个编号                      |
| `runId`               | 将任务计划、采集、存储、评分与结束汇总关联到同一次招聘更新            |
| `sourceId` / `siteId` | 定位具体来源和站点，不保存查询词或原始网址                            |
| `requestId`           | `q-` 请求编号，用于关联一次应用请求或外部请求的过程；缓存读取也有编号 |
| `parentRequestId`     | 关联格式修复等操作所依据的原请求                                      |
| `parentDiagnosticId`  | 关联上层请求失败与底层异常，避免只看到重复摘要                        |
| `sessionId`           | `s-` 启动会话编号，用于区分不同软件运行期间的记录                     |

任务与请求上下文通过异步上下文传递。并发任务的记录仍使用各自编号。面板提供级别、分类和错误编号筛选；诊断 API 还支持来源、站点、任务及请求编号筛选。

## 保留、故障降级与不完整情况

- 文件为 `logs/application.log` 与 `logs/application.previous.log`，各最多 4 MiB；写满后轮转，较早历史会被覆盖。
- 当前进程内存最多保留 1,000 条；单条文件记录最多 16 KiB，调用位置也有限长。
- 文件损坏行会被跳过，并在摘要及导出中提示。存在轮转历史时，导出明确说明早于保留范围的记录可能已覆盖。
- 文件读写失败时使用有界内存记录，并提示用户先导出。关闭或重启软件会丢失仅保存在内存的日志；这是诊断存储失败，不等同于求职数据保存失败。
- 日志观察器异常不会改变原操作的成功、失败、取消或重试语义。异步诊断等待最长约 500 ms；文件 IO 卡住时停止排队写入并使用有界内存，使查看与导出仍可返回。
- 致命异常在进程默认退出前尽力同步落盘；日志自身异常不会产生第二次异常。若此前已确认磁盘 IO 超时，致命日志不再尝试同步 IO，避免退出时再次卡住。强制结束进程、断电或不可写磁盘仍可能导致末尾记录缺失。
- 日志独立于求职数据和业务备份。业务备份含个人资料，不能用作脱敏诊断文件分享。

## 隐私与安全边界

日志在写入和读回时均检查白名单字段。错误摘要使用固定安全文本、允许的错误类型／代码、明确 HTTP 状态与相对项目代码位置；资源路径仅保留已知文件名或固定通配名称。运行环境仅保留应用、Node、Electron、Chromium、操作系统版本，以及平台、架构、是否打包等字段。

不会保存以下内容：简历及个人画像、求职关键词、招聘正文、备注、模型提示词／回复、原始 URL／查询参数、请求头、凭据、密码、Key、私人绝对路径、原始控制台输出或整份环境变量。解析记录只提供结构、长度与计数；API 地址只提供已知路由模板。

桌面界面上报仅接受当前窗口主 frame 和本机应用来源，限制操作与错误代码，单次最多 8 KiB，每分钟最多 20 次。日志读取／导出不再生成日志上报，避免递归。

诊断只能保留当时采集到的安全信息。省略了自由文本错误消息，因此排查需结合代码位置、步骤、状态和上下文编号，不能从日志还原私人输入或原始响应。
