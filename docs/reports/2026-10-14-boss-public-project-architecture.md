## 2. 实际结构比较

### boss-agent-cli：策略与浏览器生命周期分开

主要层次是“命令/业务服务 → API 客户端 → BrowserSourcePolicy → BrowserSession → 结果”。策略表定义可用通道、能否启动浏览器、能否建立上下文、能否读取存储凭据，以及失败码。

它的 [`existing-browser` 策略](https://github.com/can4hou6joeng4/boss-agent-cli/blob/v3.0.0/src/boss_agent_cli/api/browser_source.py) 禁止启动浏览器、建立新上下文或读取本地凭据。[浏览器实现](https://github.com/can4hou6joeng4/boss-agent-cli/blob/v3.0.0/src/boss_agent_cli/api/browser_client.py) 复用已有目标页，并区分页面是否由程序创建，以决定关闭时应释放什么。这种“能力许可和生命周期所有权分离”适合参考。

但这份 wheel 仍会自动探测 CDP 端口并选择第一个上下文，不能满足本项目每个目标版本的明确归属。[搜索客户端](https://github.com/can4hou6joeng4/boss-agent-cli/blob/v3.0.0/src/boss_agent_cli/api/client.py) 第 165 行使用 GET，而本项目先前现场验证的列表契约是固定 POST。BrowserSession 的通用 fetch 和上下文销毁后一次重发也不能直接替代当前网页原生客户端与禁止隐含重发的约束。默认 `auto` 通道、正文 httpx→浏览器回退、自动安全刷新均不采用。

### bosszp-crawler：监听、正文补读、分页与检查点

它在导航前注册 request/response 监听，提取列表 JSON，缺正文时打开详情页，结束后清理监听。第二页开始可能主动重放捕获的请求模板，因此不能称为纯被动读取。[监听清理](https://github.com/meetchen/bosszp-crawler/blob/2b9fe120477327b002027c38ba0c35af9952204c/boss_crawler.py#L515-L705) 的局部生命周期值得参考。

主要缺点是非 200、非 JSON、无 jobList 和验证码可能都成为空结果；重试耗尽后仍可能推进页码。检查点直接覆盖，写失败被吞掉。随机身份、失败后重建上下文和认证请求模板落盘不适合本项目。应只借鉴“成功一页后提交检查点”的概念，并使用现有事务、账本和精确响应归属。

### auto-zhipin：同页读取正文，查询混入写操作

它点击列表卡片，在同一页面等待正文区域可见后读取文本；这种同页详情步骤简洁。但它启动新上下文并导入 cookies，没有复用明确归属的当前版本页面。更重要的是，[query.py 第 43–45 行](https://github.com/ufownl/auto-zhipin/blob/09e6af1ab35e8dd2ea420e860fccc4b95642223c/query.py#L43-L45) 会自动收藏，其他入口还有沟通和发送。它的 query 不能直接作为只读采集命令运行。

## 3. 对当前项目的取舍

| 思路                                        | 取舍与理由                                                                                                 |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 策略声明与生命周期所有权分开                | 推荐。复用现有 network-policy、sessions、browser 和固定 Boss operation，避免再建立一套采集器               |
| 保留当前版本已初始化的手动页面              | 值得作为下一步设计验证。明确页面拥有者、活动、会话和租借时段；缺页时明确失败，不能借用其他版本或日常浏览器 |
| 操作专属监听、完成后释放                    | 推荐，但只采固定端点和本次 query/city/page；认证 headers/body 不进入日志                                   |
| 完整正文、身份与投递证据分别记录            | 推荐，现有质量投影继续区分列表样本、正文、仍在招和投递入口，不能仅凭列表有记录算有效岗位                   |
| 成功持久化后才推进页码                      | 推荐，沿用现有检查点与版本事务；失败、取消、风控均不能推进                                                 |
| 失败转空、随机身份、自动刷新/重试、切换后台 | 不采用。会掩盖问题或破坏已批准的停止边界                                                                   |
| 收藏、聊天、自动发送和投递                  | 不采用。本次授权是招聘数据读取                                                                             |

现有职责适合保持为：`sessions.mjs` 管会话归属；`network-policy.mjs` 管可发请求；`browser.mjs` 管窗口、计量和取消；`boss-page.mjs` 使用网页原生客户端；`protocol.mjs` 校验请求及业务响应；`records.mjs` 映射公开岗位；`source-service.mjs` 保存核验结果；IPC 只返回安全状态与诊断编号。无需引入 Python 爬虫进程或替换整个框架。

## 4. 当前真实故障与研究结论

本次真人登录后的诊断请求在北京时间 2026-10-14 20:13:11.953 返回 `boss_environment_risk`，诊断编号 `d-f6f66cfd-545c-401a-954d-af9d511a53a2`。归属该版本的风险停止标记已持久化；本次列表、正文均未取得样本。

本项目当前 `browser.mjs` 在只读读取前会关闭同会话的手动窗口并新建隐藏窗口。公开 CLI 的 existing-browser 策略保留原页面，因此原页面生命周期是一个有价值的比较点。但是“更换页面造成这次环境风控”尚未被实验证明，不能作为已找到根因或已修复风控的结论。静态源码也无法证明平台当前允许某个接口、账号仍可正常访问或分页完整。

已定位并补修的是软件反馈缺陷：Boss 错误曾在来源健康落盘前上抛，使卡片保留旧状态；IPC 原始异常也阻止界面即时呈现风险状态和诊断入口。本次修复保存版本内失败后继续让诊断活动失败，保留原错误类型，并向界面返回安全风险状态。取消、过期活动和写入失败继续优先传播。混合样本不能掩盖后续读取失败；恢复失败也必须有诊断编号。

风控恢复沿用既定流程：用户先在该版本的官方独立窗口处理限制，再由用户明确选择解除并核验；未成功验证前保持停止。研究任务没有解除停止、重试 Boss 或转换到另一通道。
